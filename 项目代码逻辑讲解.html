1. 项目总体逻辑（先看全局）

  • 入口由 Nginx 统一代理，/api/langgraph/* 走 LangGraph，其他 /api/* 走 Gateway。
  • Gateway 在生命周期中初始化运行时依赖（StreamBridge、RunManager、checkpointer、store）。
  • Lead Agent 由 make_lead_agent 动态创建，按请求上下文选择模型、工具、中间件链。
  • 工具体系可混合：内置工具 + MCP 工具 + 子代理工具；RAG 通过 MCP server 解耦接入。

来源：README_zh.md、backend/README.md、backend/langgraph.json

4. 代码链路讲解（按执行顺序）

4.1 Gateway 启动与路由装配

关键点：Gateway 在 lifespan 中加载配置并初始化 LangGraph 运行时依赖，随后挂载 models/mcp/memory/runs 等路由。

来源：backend/app/gateway/app.py、backend/app/gateway/deps.py

async with langgraph_runtime(app):
    logger.info("LangGraph runtime initialised")
    ...
app.include_router(thread_runs.router)
app.include_router(runs.router)

4.2 run 创建、SSE 流式输出

关键点：/api/threads/{thread_id}/runs/stream 和 /api/runs/stream 都会调用 start_run，然后通过 sse_consumer 把执行过程流式返回。

来源：backend/app/gateway/routers/thread_runs.py、backend/app/gateway/routers/runs.py

record = await start_run(body, thread_id, request)
return StreamingResponse(
    sse_consumer(bridge, record, request, run_mgr),
    media_type="text/event-stream",
)

4.3 Lead Agent 动态构建

关键点：make_lead_agent 会解析 runtime context（模型、plan mode、subagent 开关等），再动态拼装模型、工具和中间件链。

来源：backend/packages/harness/deerflow/agents/lead_agent/agent.py、backend/langgraph.json

4.6 子代理执行机制（task_tool -> SubagentExecutor）

关键点：task_tool 会创建后台任务并轮询状态，执行过程中把子代理消息实时回灌给主流；SubagentExecutor 在独立线程池+事件循环中运行，避免阻塞主链路。

来源：backend/packages/harness/deerflow/tools/builtins/task_tool.py、backend/packages/harness/deerflow/subagents/executor.py

task_id = executor.execute_async(prompt, task_id=tool_call_id)
while True:
    result = get_background_task_result(task_id)
    if result.status == SubagentStatus.COMPLETED:
        return f"Task Succeeded. Result: {result.result}"

5. RAG 模块（MCP Server）逻辑说明

当前项目的 RAG 采用 MCP 解耦接入。主流程是两段式：

  • search_knowledge：向量检索 + 轻量词法重排 + token 预算裁剪，返回摘要与 source_id。

6. 权限控制（Guardrail）在链路中的位置

权限不是“路由层拦截”，而是 工具调用前拦截。GuardrailMiddleware 在 wrap_tool_call / awrap_tool_call 中向 provider 询问决策，拒绝时返回 error 类型 ToolMessage，让 Agent 改用替代方案。

来源：backend/packages/harness/deerflow/guardrails/middleware.py、docs/权限控制.md

decision = self.provider.evaluate(gr)
if not decision.allow:
    return ToolMessage(
      content="Guardrail denied: ...",
      status="error",
    )

文档中的策略建议采用 默认拒绝 + deny 优先于 allow，并统一资源命名：tool:* / kb:namespace:kb_id / mcp:server:tool。

7. 一句话总结代码主逻辑

DeerFlow 2 的核心是：Gateway 负责 API 与运行时编排，Lead Agent 负责“模型+中间件+工具”的动态装配，工具层通过 Sandbox/MCP/Subagent 提供执行能力，RAG 与权限控制通过可插拔模块接入并在工具调用阶段生效。

8. 最近两次问答整理（增补）

8.1 问题一：发起一次请求直接调用自定义工具，路径与 LLM 次数

  • 执行路径：用户请求 -> Gateway runs 路由 -> start_run -> make_lead_agent -> LLM 决策 tool call -> 自定义工具执行 -> LLM 汇总输出 -> SSE 回传。
  • 常见 LLM 次数为 2 次：第一次“决定调工具”，第二次“根据工具结果生成回答”。
  • 边界情况：不调工具时可能 1 次；多工具串行/并行或中间件触发额外调用时可超过 2 次。

对应代码：backend/app/gateway/routers/thread_runs.py、backend/packages/harness/deerflow/agents/lead_agent/agent.py、backend/packages/harness/deerflow/tools/tools.py

8.2 问题二：是否支持“复杂任务高阶模型、总结任务低成本模型”

  • 项目支持多模型配置（models 多项）。
  • 支持模块级模型拆分：summarization.model_name、title.model_name、memory.model_name、subagents.agents.*.model。
  • 主 run 的 lead agent 通常使用单一解析后的主模型；总结类与子代理可独立配置模型。

对应代码：backend/packages/harness/deerflow/agents/lead_agent/agent.py、backend/packages/harness/deerflow/subagents/executor.py、config.example.yaml

9.2 你环境下的“精确最小/最大 LLM 次数表”

范围定义：单次用户请求（一次 run），不启用 subagent、不触发额外重试，按当前默认开关推导。

场景A：模型直接回答（不调用任何工具）
- 最小：1（主模型回答）
- 最大：4（主模型 + title + summarization + memory）

场景B：调用 1 个工具并结束
- 最小：2（主模型决策工具 + 主模型整合结果）
- 最大：5（上面2次 + title + summarization + memory）

场景C：调用 N 个工具（串行轮次）
- 最小：N + 1
  解释：每次工具前至少1次模型决策，最后1次总结输出
- 最大：N + 4
  解释：主链路 N+1 次，再叠加 title/summarization/memory 各最多1次

注：summarization 只有在触发阈值达到时才会额外调用；memory 为异步更新链路，通常不会阻塞主响应但仍属于该次对话触发的 LLM 开销。
