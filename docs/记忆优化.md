# 记忆优化方案（企业版整理）

本文档整理 DeerFlow **记忆能力**的企业级演进方向：在**保留现有框架行为**的前提下，引入 **PostgreSQL** 存储长期记忆与工作记忆的权威数据，并与 **身份 / 租户横切** 对齐；**长期记忆**采用 **双轨**：**结构化 JSON/事实**（`memory_long_term`，权威）+ **同库 pgvector（或其它向量引擎；文档默认写「PG 内向量扩展」）** 做语义召回（见 **§4.1.1**）。**工作记忆**采用 **分层策略**（类比 CPU L1/L2/L3）：**L1 活跃上下文在 Prompt**，**L2 会话状态在 Redis（键值）+ PG 持久**，**L3 本会话归档语义按需召回**（见 **§3.1**，与长期向量索引分工不同）；同时约定 **历史记忆召回强度可配置**（§7，含可选语义检索）。

---

## 1. 目标与原则

| 目标 | 说明 |
|------|------|
| 长期记忆 | **双轨**：跨会话画像、时间维度摘要、`facts` 等与当前 `memory.json` **同构**的权威数据存 **`memory_long_term`（PG JSONB）**；**pgvector**（PG 内向量扩展）对 **摘要段落、facts 文本、归档块** 建 embedding，**仅作语义召回辅助**，**不替代** JSON/事实权威。 |
| 工作记忆 | 按 `thread_id` 的会话上下文；**分层**：L1 Prompt / L2 Redis+PG（键值）/ L3 **本会话**向量归档按需检索（**§3.1**）；L2 主路径**非向量**（§4.2.1）。 |
| 权限横切 | 所有读写绑定 **`tenant_id` + `subject`**（来自网关鉴权，注入 `runtime.context`）；库侧 RLS + 应用层强制过滤。 |
| 保留框架 | **不推翻** `MemoryMiddleware`、`MemoryUpdateQueue`、`MemoryUpdater`、`_apply_updates`、`format_memory_for_injection`、facts 置信度/去重、`max_facts`、上传相关清洗、correction/reinforcement 等语义；仅替换 **`MemoryStorage` 实现**、在 **`save` 成功后（或异步队列）** 维护向量索引，并扩展注入前的**数据组装与可配置召回策略**（含可选语义 Top-K）。 |

**非目标（与记忆正交）**：LangGraph checkpoint、对话 `summarization` 配置、Skills 文件体系——仅做分工说明，不在此替代。

---

## 2. 现状框架（简要）

- **写入**：`MemoryMiddleware` 在 `after_agent` 将过滤后的对话入队 → `debounce_seconds` 防抖 → `MemoryUpdater` 调 LLM 按 `MEMORY_UPDATE_PROMPT` 产出 JSON → `_apply_updates` 合并 → `MemoryStorage.save`。
- **读取**：主智能体系统提示通过 `_get_memory_context` → `get_memory_data` → `format_memory_for_injection`（受 `max_injection_tokens` 等约束）。
- **默认存储**：`FileMemoryStorage`（`config.yaml` 中 `memory.storage_class` 可替换）。

---

## 3. 目标架构

```
[Gateway 鉴权] → tenant_id, subject 写入 runtime.context
        ↓
[MemoryMiddleware] → 防抖队列（逻辑不变）
        ↓
[MemoryUpdater] → LLM 合并（逻辑不变）→ _apply_updates（逻辑不变）
        ↓
[PostgresMemoryStorage.save] → 事务写 memory_long_term + memory_working
        │                              ↓（事务成功提交后）
        │                         [Redis] 更新/失效 working 缓存（非向量，键值 JSON）
        │                              ↓（同一成功路径，同步或异步）
        │                         [pgvector] 自长期记忆权威 payload 抽取可嵌入单元 → 更新语义索引（§4.1.1）
        ↑
[注入] load → long_term 读 PG；working 优先 Redis、miss 则 PG 回填
            → 合并 → 按「召回配置」裁剪 → format_memory_for_injection（构成 L1 的主路径）
            → 【可选，配置项】按本轮 query 语义检索 pgvector Top-K → 压缩后并入 L1（§7）
[L3 可选] 本会话向量归档 ← 下沉（策略触发）；读路径：检索工具 → 节选 → 提升回 L1（与 §4.1.1 长期索引分工，见 §3.1.2）
```

长期记忆以 **PG 表 `memory_long_term` 中 JSONB 为唯一权威**；**pgvector** 为 **双轨中的语义召回层**（§4.1.1），**不**作为事实合并与去重的数据源。若需热点加速可另议只读副本，本文不强制 Redis。工作记忆 **L2：Redis + PG** 见 **§4.2.1**；**L1/L2/L3 分层动机与数据流**见 **§3.1**。

---

## 3.1 工作记忆分层存储（与本文方案整合）

### 3.1.1 核心动机

大模型**上下文窗口有限**，且上下文过长会带来推理变慢、成本上升与「中间迷失」等问题。工作记忆若不分级，容易把「全部历史」塞进 Prompt，既浪费容量又降低质量。  
**工作记忆分层存储**是在**窗口有限**与**任务复杂度无限**之间的矛盾下，对会话相关数据做的**分级管理**：**越核心、越高频**的信息离模型越近；**次要、低频、档案型**信息外置，**需要时再召回**。

可类比 **CPU 缓存体系（L1 / L2 / L3）**：

| 层级 | 类比 | 特征 |
|------|------|------|
| 第一层（L1） | 寄存器 / L1 Cache | 容量最小、**延迟最低**，直接参与当前推理 |
| 第二层（L2） | L2 Cache | 容量中等、**读写极快**，手边状态与会话摘要 |
| 第三层（L3） | L3 / 内存外存 | 容量大、**访问较慢**，档案与语义检索 |

---

### 3.1.2 三层架构（企业落地）

#### 第一层：活跃上下文（模型原生层 / L1）

- **存储位置**：直接拼入发给 LLM 的 **Prompt**（系统提示 + 本轮可注入块）。
- **典型内容**：
  - 系统指令与 Agent 角色；
  - **当前步骤**与任务焦点；
  - **最近 1～3 轮**用户与助手对话（与现有 **summarization** 压缩后的消息窗口协同）；
  - **关键变量**（如订单号、当前工具必需参数）；
  - 经 **`memory.recall` 裁剪后**注入的长期记忆片段与工作记忆片段（§7）；以及 **配置开启时**，经 **pgvector** 语义检索并压缩后的长期记忆补充块（§4.1.1、§7）。
- **特点**：容量受 **Token** 严格约束；成本与延迟最高；必须保持「少而准」。

#### 第二层：会话状态缓存（Redis / 内存层 / L2）

- **存储位置**：**Redis**（或同类内存缓存）；**权威持久化**仍用 **PostgreSQL `memory_working`**（§4.2、§4.2.1）。
- **典型内容**：
  - **较早轮次的对话摘要**（例如第 4 轮以前的压缩叙述，而非全文）；
  - **长任务进度**（如「步骤 2/5」、中间结论）；
  - **本次会话临时素材**的索引或短摘要（大文件本体可仍在对象存储 / 线程目录，L2 仅存可检索指针或摘要）。
- **特点**：**键值、非向量**为主（与 §4.2.1 一致）；当 L1 装不下时，可将「刚被挤出窗口」的摘要**下沉**到 L2；读写快，可配 **TTL**。

#### 第三层：本会话归档（向量检索层 / L3）

- **存储位置**：**向量索引**（可与长期记忆共用 **PG + pgvector** 同一实例，以 **元数据** 区分 `scope=working_archive` 与 `scope=long_term`；或使用 **Milvus / Pinecone** 等独立引擎）。**与长期记忆双轨的关系**：**长期**侧结构化 + 语义索引见 **§4.1.1**；**L3** 侧重 **本会话（`thread_id`）** 内、尚未或不会进入 `memory_long_term` 的档案型片段。
- **典型内容**：
  - **本会话更早轮次的详细对话片段**、长文档切块；
  - 需按**语义相似度**召回的会话内细节，而非仅按 L2 单键直读 JSON。
- **特点**：容量可扩展；检索相对慢；**默认不整库灌入 Prompt**。可由 **服务端注入管线**或 Agent **按需调用检索工具**（或 MCP）将 Top-K 结果**压缩后提升回 L1**。
- **与「工作记忆非向量」的关系**：**工作记忆的主路径（L2）仍不采用向量**；L3 是**会话侧**归档与语义补充层。**长期记忆**的语义召回优先走 **§4.1.1**（与权威 JSON 同源维护），避免与 L3 职责混淆。

---

### 3.1.3 数据流动（动态管理）

**写入（膨胀与下沉）**

1. 用户新输入 → 先进入 **L1**（消息列表 + 当前轮次）。
2. L1 接近或超过策略阈值（Token / 轮数）→ 触发 **压缩**（现有 **summarization**、或会话级摘要写入 **L2** 的 `session_summary` 等）。
3. L2 中**本会话仍需保留且适合语义检索**、又**不宜写入长期记忆 JSON**的片段（可选策略）→ **归档索引**到 **L3**（带 `tenant_id`、`subject`、`thread_id` 等元数据，便于过滤）。**已进入长期记忆权威 JSON 的摘要 / facts** 的语义索引维护见 **§4.1.1**，不必重复写入 L3，除非企业策略要求「会话视角」副本。

**读取（召回与提升）**

1. Agent 推理时**默认只读 L1**。
2. 若 L1/L2 中仅有摘要、需要**本会话**细节 → 用 **查询意图** 调 **L3 向量检索** → 将命中块**压缩或节选后写入 L1**（或作为 tool 结果进入下一轮）。
3. **结构化长期画像**仍以 **`memory_long_term` + `format_memory_for_injection`** 为主路径进入 L1（受 §7 `recall` 约束）；**可选**再叠加 **§4.1.1 pgvector** 按 query 的 Top-K 命中（§7 配置），与 L3 **互补**：长期向量偏 **与权威 JSON 同源的摘要段 / facts / 归档块**，L3 偏 **会话内**档案。

---

### 3.1.4 与本文 PostgreSQL / Redis / 权限方案的关系（一览）

| 概念层 | 技术落点（本文） | 租户 / 权限 |
|--------|------------------|-------------|
| L1 | Prompt 拼装、`memory.recall`、`summarization` 窗口 | 仅服务端组装；不信任客户端自报租户 |
| L2 | Redis 键值 + `memory_working`（PG） | Key/PG 行均带 `tenant_id`、`subject` |
| L3 | 会话归档向量索引 + 元数据过滤（可与 pgvector 同库不同 scope） | 集合/索引按租户隔离或强制 metadata filter |
| 结构化长期记忆 | `memory_long_term`（PG JSONB），权威 | RLS + 应用层校验（§4、§8） |
| 长期语义召回 | **pgvector**（与 PG 同实例或企业另选向量引擎） | 与长期表同源更新；RLS / `tenant_id`+`subject` 过滤；**只读辅助** |

---

### 3.1.5 小结（分层策略）

- **好钢用在刀刃上**：最紧急、最相关的信息在 **L1（Prompt）**；次要背景在 **L2（Redis + PG 工作记忆）**；**本会话**历史档案在 **L3（向量，按需召回）**；**跨会话长期**语义补充在 **§4.1.1（pgvector，按需并入 L1）**。
- 这样可在**超长任务**下既减少「健忘」（数据仍在 L2/L3），又避免 Prompt **被低价值信息塞满**而「变笨」。
- 实现上可分阶段：**先做 L1 裁剪（§7）+ L2（§4.2.1）+ PG 双表**；**长期 pgvector 索引（§4.1.1）** 与 **L3 会话归档** 可按企业需要分步上线。

## 4. PostgreSQL 逻辑模型（建议）

### 4.1 表 `memory_long_term`

- `tenant_id`、`subject`、`agent_name`（可空，与「按 agent 分文件」对齐）、`version`（乐观锁）、`payload` JSONB（与现有 `user` / `history` / `facts` 同构）、`updated_at`。
- 唯一约束：`UNIQUE(tenant_id, subject, agent_name)`（全局记忆可用空串占位，避免 UNIQUE 与 NULL 歧义）。
- **权威语义**：**合并、去重、置信度、`max_facts`、注入前结构化裁剪** 一律以本行 **`payload`** 为准；**向量表仅镜像可检索文本，不参与事实裁决**。

### 4.1.1 长期记忆语义索引（pgvector 双轨）

在 **同一 PostgreSQL 实例**上启用 **`pgvector` 扩展**（企业若选用 Milvus / Pinecone 等，仍建议保持「**结构化权威在 PG、向量侧存嵌入与元数据**」的同构思路；本文默认描述 **PG 内向量扩展**）。

**辅助表（示例）`memory_long_term_embedding`**（名称可自定）建议字段：

- 维度：`tenant_id`、`subject`、`agent_name`（可空，与长期表对齐）、`chunk_id`（稳定主键或 UUID）、`source_kind`（如 `summary` / `fact` / `archive_chunk`）、`ref`（可选：JSON 内路径或 `fact.id` 等便于溯源）、`content_text`（被嵌入的明文）、`embedding`（`vector`）、`payload_version`（可选，与 `memory_long_term.version` 对齐便于失效）、`updated_at`。
- 索引：HNSW / IVFFlat 等按 pgvector 版本与数据量选型；**查询必须带** `tenant_id` + `subject`（及按需 `agent_name`）**过滤**，与 RLS 一致。

**嵌入对象**：从已成功持久化的 **`payload`** 派生，例如：

- **摘要段落**：`user.*.summary`、`history.*.summary` 等非空文本；
- **facts 文本**：每条 fact 的 `content`（可与 `id` 绑定为独立 chunk）；
- **归档块**：企业若将部分长文本拆块写入 JSON 侧字段，可按块嵌入（需在方案中固定切块策略与 `ref` 规则）。

**写入时机**（与现网管线对齐）：

1. `MemoryUpdater` **`_apply_updates` 合并完成** 且 **`MemoryStorage.save` 事务提交成功**之后；
2. **同步**：同一请求路径内重算受影响 chunk 并 `UPSERT` 向量行（延迟敏感场景慎用）；
3. **异步（推荐）**：将 `(tenant_id, subject, agent_name, new_version)` 入队，由 worker 拉取最新 `payload`、diff 或全量重建嵌入，失败可重试；**不得**在 `save` 失败时更新向量，避免权威与索引不一致。

**读取时机**（注入前）：

1. **主路径不变**：`get_memory_data` → **`format_memory_for_injection`**（受 `max_injection_tokens` 与 §7 `recall` 约束）；
2. **可选（配置项）**：当 **`memory.recall.semantic_retrieval.enabled`** 为真时，用 **本轮 query**（默认取最近用户消息文本，或企业指定字段）对 **`memory_long_term_embedding`** 做相似度检索，取 **Top-K**，经 **压缩/截断** 后与结构化注入块 **合并入 L1**（总长度仍受 `max_injection_tokens` 或单独 `max_semantic_chars` 限制）。

**与 L3 分工**：本节仅服务 **长期记忆** 权威数据派生的语义召回；**本会话**专属、未进入 `memory_long_term` 的片段仍由 **§3.1 L3** 或等价机制承载，避免单一索引混杂 scope 时丢失过滤能力（若采用**统一向量表**，须用 `scope` / `thread_id` 等列严格区分查询）。

### 4.2 表 `memory_working`

- `tenant_id`、`subject`、`thread_id`、`agent_name`（可空）、`payload` JSONB（如 `session_summary`、`focus`、`open_items` 等）、`updated_at`。
- 唯一约束：`UNIQUE(tenant_id, subject, thread_id, agent_name)`。

#### 4.2.1 工作记忆（L2）：非向量；推荐 **Redis 缓存 + PG 持久**

- **L2 主路径不使用向量存储**：会话工作记忆按 **`tenant_id` + `subject` + `thread_id`** **精确键**读写，形态为小段 JSON（会话摘要、焦点、进度等），不是「在全库按语义相似度 Top-K 检索」。**本会话**向量归档适合 **L3**（§3.1.2）；**长期记忆**侧语义索引为 **§4.1.1**，与 L2 键值正交。若把 L2 默认绑在向量存储上 **不合理**（复杂度高、延迟与成本难控，且与键值访问模式不匹配）。
- **推荐组合**：
  - **PostgreSQL（`memory_working`）**：权威数据、审计、备份与 RLS 与长期记忆一致，便于统一运维。
  - **Redis**：热路径缓存（Cache-Aside）。Key 建议带租户隔离前缀，例如 `memory:working:{tenant_id}:{subject}:{thread_id}`（必要时含 `agent_name`），值为序列化后的 `payload` JSON；配置 **TTL**（如与会话生命周期对齐），会话结束可自动淘汰，符合「短期、可丢可重建」的特点。
- **读写顺序（建议）**：
  - **读**：先 Redis，未命中再查 PG，回填 Redis（带 TTL）。
  - **写**：先写 PG（事务成功），再 **删除或更新** Redis 对应 key，避免脏缓存长期存在。
- **降级**：Redis 不可用时可直接走 PG，仅失去加速与 TTL 自动清理（需依赖业务侧清理或 PG 保留策略）。

### 4.3 安全

- 启用 **RLS**，`tenant_id`（及普通用户的 `subject`）与 `current_setting('app.*')` 对齐；应用连接使用**最小权限**库账号。
- **`memory_long_term_embedding`（§4.1.1）** 与长期主表采用**同等租户隔离策略**；检索 SQL **必须**带与主表一致的过滤条件，避免仅靠向量相似度跨租户命中。

## 5. `MemoryStorage` 职责（PG 实现）

- **`load`**：长期记忆仅从 **PG** 读取；工作记忆 **先 Redis、miss 再 PG** 并可选回填 Redis（见 §4.2.1）。将两路结果组装为与 `create_empty_memory()` **兼容**的 dict，并附带工作记忆段供注入层消费。**语义检索**在注入层按需发起（§4.1.1、§7），**不必**在 `load` 中默认拉取向量。
- **`save`**：将 LLM 合并结果拆分写入 PG（`memory_long_term` + `memory_working`）；**`save` 前**仍执行现有 `max_facts` 截断、去重、`_strip_upload_mentions_from_memory`。工作记忆在 PG 提交成功后 **更新或删除** Redis 中对应 key，保证缓存与权威一致。**在 `save` 事务成功提交之后**（同步或经队列异步）触发 **§4.1.1** 向量索引更新，使嵌入与最新 **`payload`** 对齐。
- **并发**：`UPDATE ... WHERE version = $v`，失败则重试或合并策略由企业策略定；向量重建应以 **已成功提交的 `version`** 为准，避免脏读写入索引。

**上下文传递**：`tenant_id` / `subject` / `thread_id` 由 Gateway 注入 `runtime.context`，经 `MemoryMiddleware` / `MemoryUpdater` 与存储层约定一致（可用 `contextvars` 避免大面积改方法签名）。

## 6. 长期记忆 vs 工作记忆（写入策略）

| 类型 | 建议写入来源 |
|------|----------------|
| 长期记忆 | 仍以 `MemoryUpdater` 为主（与现网一致）；**权威**存 **`memory_long_term`（PG JSONB）**；**语义索引**为 **§4.1.1 pgvector**，在 **`save` 成功后**同步或异步更新，**不替代** JSON/事实管线。 |
| 工作记忆 | **方案 A**：扩展 LLM 输出块，一次事务写 PG 两表；**方案 B**：独立轻量任务按轮次/阈值更新 `session_summary`（与 `summarization` 分工：后者压消息列表，前者压可注入会话摘要）。写入 PG 后按 **§4.2.1** 维护 **Redis** 缓存（非向量键值）。 |

**存储选型小结**：工作记忆 **L2 不采用向量存储**；**Redis（缓存）+ PostgreSQL（持久化）** 为 L2 推荐默认组合。**长期记忆**为 **PG 结构化 + pgvector 双轨**（§4.1、§4.1.1）。**L3** 面向 **本会话**归档向量，见 **§3.1**。

## 7. 历史记忆召回 — **可配置化**（本文档强制要求）

在「注入」阶段，除全局 **`max_injection_tokens`** 外，应支持**显式数量/条数上限**（结构化块），并**可选**启用 **长期 pgvector** 语义召回（§4.1.1），便于企业按成本与隐私分级调节「懂用户」的强度。

### 7.1 建议在 `config.yaml` 的 `memory` 下增加 `recall` 段

下列项为**方案约定**；落地时在 `MemoryConfig`（`backend/packages/harness/deerflow/config/memory_config.py`）与 `format_memory_for_injection`（及注入前可选的 **pgvector** 检索步骤）中实现。

```yaml
memory:
  enabled: true
  injection_enabled: true
  max_injection_tokens: 2000
  max_facts: 100
  fact_confidence_threshold: 0.7
  debounce_seconds: 30
  model_name: null
  storage_class: deerflow.agents.memory.storage.FileMemoryStorage

  # 历史记忆召回（注入前裁剪策略，与 max_injection_tokens 同时生效：先按条数/段数上限取，再按 token 截断）
  recall:
    # 注入时最多纳入的「事实」条数（按 confidence 降序取前 N；0 表示不限制条数，仅受 max_injection_tokens 约束）
    max_facts_injection: 20
    # 长期记忆中「history」区块最多注入几段（按固定顺序：recentMonths → earlierContext → longTermBackground；1~3）
    max_history_sections: 3
    # 「user」上下文区块最多注入几段（顺序：workContext → personalContext → topOfMind；0~3）
    max_user_sections: 3
    # 若存在工作记忆，是否注入及最大字符数（0 表示不注入工作记忆）
    working_memory_enabled: true
    working_memory_max_chars: 1200

    # 长期记忆 pgvector 语义召回（可选；在 format_memory_for_injection 结构化块之后合并，仍受总预算约束）
    semantic_retrieval:
      enabled: false
      # 相似度检索 Top-K（仅查 memory_long_term_embedding，且强制 tenant_id + subject 过滤）
      top_k: 5
      # 命中块压缩/拼接后进入 L1 的最大字符数（0 表示关闭字符上限，仍建议与 max_injection_tokens 联动截断）
      max_semantic_chars: 800
      # query 来源：如 "last_user_message"（默认）或企业自定义字段名
      query_source: last_user_message
```

### 7.2 语义说明

| 配置项 | 作用 |
|--------|------|
| `max_facts_injection` | 控制**历史事实**进入提示的**条数上限**，避免 facts 过多挤占其它上下文。 |
| `max_history_sections` | 控制**时间维度摘要**进入提示的**段数**（多段合并仍受 `max_injection_tokens` 限制）。 |
| `max_user_sections` | 控制**用户画像摘要**进入提示的**段数**。 |
| `working_memory_enabled` / `working_memory_max_chars` | 控制**工作记忆**是否及多长进入提示（与 PG `memory_working` 对应）。 |
| `semantic_retrieval.enabled` | 是否启用 **§4.1.1** 长期记忆向量检索；关闭时行为与仅结构化注入一致。 |
| `semantic_retrieval.top_k` | 语义检索返回条数上限。 |
| `semantic_retrieval.max_semantic_chars` | Top-K 结果压缩合并后的字符上限，防止挤占 L1。 |
| `semantic_retrieval.query_source` | 检索 query 的来源（如最近用户输入），避免客户端随意指定查询串时须配合网关策略。 |

**优先级建议**：先按 `recall` **条数/段数**完成 **`format_memory_for_injection`**；若启用 **`semantic_retrieval`**，再检索、压缩、**拼接**至注入块；最后统一执行 **`max_injection_tokens`**（及 `max_semantic_chars`）截断，保证行为可预测。

## 8. 与权限横切的关系（摘要）

- 身份只信网关解析结果；客户端不可单独作为 `tenant_id` 信任源。
- 所有 PG 访问必须带 `tenant_id`；RLS 作为第二道防线。
- 多副本部署时 Gateway 与 LangGraph 侧 **`tenant_id` / `subject` 传递一致**，避免写错租户。

## 9. 实施阶段建议

1. DDL、RLS、迁移脚本（含自 `memory.json` 导入）；**安装 `pgvector` 扩展**及 **§4.1.1** 辅助表、向量索引。
2. 实现 `PostgresMemoryStorage` 与连接池配置；工作记忆 **L2** 接入 **Redis**（TTL、key 规范、失效策略），见 §4.2.1。
3. 打通 `runtime.context` → 存储层。
4. 实现 **`memory.recall`** 配置项并接入 `format_memory_for_injection`（或薄封装层），落实 **L1** 注入预算。
5. 实现 **`save` 成功后**（同步或队列）**嵌入流水线**：从 `payload` 生成 chunk、调用嵌入模型、`UPSERT` **§4.1.1**；与 `version` 对齐的失效/全量重建策略。
6. 实现 **`memory.recall.semantic_retrieval`**：注入前 **可选** pgvector 查询、Top-K 压缩、与结构化块合并及总预算截断。
7. 与现有 **summarization** 对齐 L1↔L2 下沉策略（轮次/Token 阈值可配置）。
8. **可选**：**L3** 本会话向量归档、元数据租户隔离、检索工具/MCP 将结果提升回 L1。
9. 压测、乐观锁冲突监控、审计与备份策略；验证 Redis 降级为仅 PG 时的行为；验证向量索引滞后/失败时 **仅结构化注入**仍可工作。

## 10. 小结

- **PostgreSQL 双表**承载**结构化长期记忆**与 **L2 工作记忆**的**权威数据**；**`MemoryStorage` 替换**即可保留现有记忆管线。**长期记忆**另以 **§4.1.1 pgvector** 做**语义双轨**，**写入在 `save` 成功之后**，**读入在注入前可选**（§7 `semantic_retrieval`），**权威仍为 JSON/事实**。
- **工作记忆分层（§3.1）**：**L1** 为 Prompt 活跃上下文（配合 **§7 recall**、可选语义块与 **summarization**）；**L2** 为 **Redis + PG**，**非向量**、键值会话态（§4.2.1）；**L3** 为**可选**本会话向量归档，**按需检索**灌入 L1，与 **长期 pgvector** 分工明确。
- **历史记忆召回可配置**：通过 **`memory.recall`** 限制结构化注入的 facts 条数、history/user 段数及工作记忆开关与长度；**可选** **`semantic_retrieval`** 控制长期向量 Top-K 与字符预算；均与 **`max_injection_tokens`** 协同，服务 **L1** 容量控制。
- 同一 `subject` 持续使用可形成稳定的「越用越贴用户」体验；强度由 **分层下沉/召回策略 + `recall` + `semantic_retrieval` + `max_injection_tokens` + `max_facts`** 联合调节。
