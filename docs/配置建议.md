# DeerFlow 配置建议

本文整理推荐的配置分工、加载机制、修改流程与 MCP 注册方式，便于团队统一执行。

---

## 1. 文件分工（推荐）

| 内容 | 文件 | 原则 |
|------|------|------|
| API Key、密码、Token 等秘密 | **`.env`** | 不写进仓库；在 YAML/JSON 中用 `$VAR` 引用 |
| 模型、工具、sandbox、memory、title、summarization 等主应用行为 | **`config.yaml`**（由 `config.example.yaml` 复制生成） | 可版本管理；敏感值一律 `$ENV` |
| MCP 服务、技能开关、拦截器 | **`extensions_config.json`**（由 `extensions_config.example.json` 复制） | 与主配置分离，见 `backend/docs/MCP_SERVER.md` |

可选环境变量：

- **`DEER_FLOW_CONFIG_PATH`**：显式指定 `config.yaml` 路径。
- **`DEER_FLOW_EXTENSIONS_CONFIG_PATH`**：显式指定扩展配置文件路径。

实现位置：`backend/packages/harness/deerflow/config/app_config.py`、`backend/packages/harness/deerflow/config/extensions_config.py`。

---

## 2. 配置如何进入进程（简要）

1. **`.env`**：在首次 `import deerflow.config.app_config` 时，模块顶层会执行 `load_dotenv()`，将变量写入 `os.environ`。
2. **`config.yaml`**：业务代码通过 `get_app_config()` 读取；首次调用时 `yaml.safe_load`，再递归执行 **`resolve_env_variables`**，把形如 `$OPENAI_API_KEY` 的字符串替换为 `os.getenv` 结果（变量缺失会报错）。
3. **`extensions_config.json`**：在 `AppConfig.from_file()` 内通过 `ExtensionsConfig.from_file()` 加载，合并进 `AppConfig.extensions`。
4. **热更新**：`get_app_config()` 会对比 `config.yaml` 的修改时间，变更后自动重载；也可用 `reload_app_config()`。MCP 侧 Gateway 在更新配置后会 `reload_extensions_config()`；LangGraph 进程是否立即感知取决于部署方式，**改 MCP 后建议重启 LangGraph（或全栈）一次**，最省心。

更细的时序可参考仓库根目录 `项目代码逻辑讲解.html` 中的「6A. 配置加载」一节。

---

## 3. 首次生成本地配置

仓库提供跨平台脚本，等价于 `make config`：

```powershell
cd <项目根目录>
python scripts\configure.py
```

若本机无 `python`，可尝试 `py scripts\configure.py`。  
若已存在 `config.yaml`，脚本会报错退出，避免覆盖。

---

## 4. 日常修改主配置（`config.yaml` + `.env`）

1. 在 **`.env`** 中维护所有密钥与可轮换的端点凭据。
2. 在 **`config.yaml`** 中只写非秘密参数，密钥字段使用 `$变量名`。
3. 与模板对齐、合并新字段时，在具备 **Git Bash** 的环境执行：

   ```bash
   make config-upgrade
   ```

4. 修改模型、sandbox、工具列表、memory 等后，**重启 Gateway + LangGraph**（或整套 `make dev` / Docker），避免旧进程持有旧配置。

## 4A. 多模型分工建议

项目已支持“主任务高阶模型 + 总结类低成本模型 + 指定 subagent 更强模型”的分工方式，建议按下述原则配置：

- `models` 支持多项，建议把主模型放在第一项作为默认 lead agent 模型。
- `summarization.model_name`、`title.model_name`、`memory.model_name` 可以独立指定低成本模型。
- `subagents.agents.<name>.model` 可为特定子代理单独指定更强模型；也可用 `inherit` 继承父模型。
- 主 run 的 lead agent 通常使用一次解析后的主模型，不会按“任务复杂度”自动切换到别的模型；需要通过配置静态分工。

与当前 `config.yaml` 字段对齐说明：

- `title.model_name` / `summarization.model_name` / `memory.model_name` 均支持 `null`（表示回退到 `models` 第一项默认模型）。
- `subagents.agents.<name>.model` 的值需要是 `models` 中已定义的 `name`，或使用 `inherit`。
- 模型超时字段名与 provider 相关：`langchain_openai:ChatOpenAI` 常用 `request_timeout`，其他 provider 可能使用 `timeout` 或 `default_request_timeout`，请以该 provider 示例字段为准。

## 4B. 可落地模板（整理自代码逻辑讲解 10）

下面是“主模型高阶 + 总结类低成本 + 某 subagent 超强”的可拷贝片段，可按现网模型名替换：

```yaml
models:
  - name: main-pro
    display_name: Main Pro (高阶主模型)
    use: langchain_openai:ChatOpenAI
    model: gpt-4.1
    api_key: $OPENAI_API_KEY
    request_timeout: 600.0
    max_retries: 2
    max_tokens: 8192
    supports_thinking: true
    supports_vision: true
    supports_reasoning_effort: true

  - name: econ-mini
    display_name: Economy Mini (低成本辅助)
    use: langchain_openai:ChatOpenAI
    model: gpt-4o-mini
    api_key: $OPENAI_API_KEY
    request_timeout: 300.0
    max_retries: 2
    max_tokens: 4096
    supports_thinking: false
    supports_vision: false

  - name: ultra-reasoner
    display_name: Ultra Reasoner (超强子代理)
    use: langchain_openai:ChatOpenAI
    model: o3
    api_key: $OPENAI_API_KEY
    request_timeout: 900.0
    max_retries: 2
    max_tokens: 16384
    supports_thinking: true
    supports_vision: true
    supports_reasoning_effort: true

title:
  enabled: true
  max_words: 6
  max_chars: 60
  model_name: econ-mini

summarization:
  enabled: true
  model_name: econ-mini
  trigger:
    - type: tokens
      value: 15564
  keep:
    type: messages
    value: 10
  trim_tokens_to_summarize: 15564

memory:
  enabled: true
  storage_path: memory.json
  debounce_seconds: 30
  model_name: econ-mini
  max_facts: 100
  fact_confidence_threshold: 0.7
  injection_enabled: true
  max_injection_tokens: 2000

subagents:
  timeout_seconds: 900
  agents:
    general-purpose:
      model: ultra-reasoner
      timeout_seconds: 1800
      max_turns: 160
    bash:
      model: inherit
      timeout_seconds: 300
      max_turns: 80
```

上面示例已按你当前 `config.yaml` 的实际键名对齐：`model_name`、`trim_tokens_to_summarize`、`fact_confidence_threshold`、`max_injection_tokens`、`subagents.agents.<name>.model/timeout_seconds/max_turns` 均与现版本一致。

落地提醒：

- 先用静态分工方案（主模型/低成本辅助/subagent 超强）稳定成本与效果。
- 再按业务场景微调 `summarization` 阈值、`memory` 注入上限和 `subagents` 的超时/轮次。

## 5. 注册与维护 MCP（推荐流程）

### 5.1 文件方式（适合 Git 与 Code Review）

1. 复制 `extensions_config.example.json` → 项目根目录 **`extensions_config.json`**。
2. 在 `mcpServers` 中增加条目，例如 `stdio`：

   ```json
   "rag-kb": {
     "enabled": true,
     "type": "stdio",
     "command": "python",
     "args": ["./mcp_servers/rag_kb_server.py"],
     "env": {
       "RAG_DB_URL": "$RAG_DB_URL",
       "RAG_EMBEDDING_API_KEY": "$RAG_EMBEDDING_API_KEY"
     },
     "description": "RAG MCP（search + expand）"
   }
   ```

3. 在 **`.env`** 中补齐上述变量；JSON 内继续用 `$VAR` 引用。
4. 保存后 **重启服务**（至少重启运行 agent 的 LangGraph 进程）。

RAG 两阶段工具示例与表结构说明见：`docs/RAG相关.md`。

### 5.2 HTTP 方式（适合运维脚本或前端设置页）

- `GET /api/mcp/config` — 读取当前 MCP 配置（Gateway）。
- `PUT /api/mcp/config` — 写入磁盘上的扩展配置文件，并 `reload_extensions_config()`；会保留当前 **skills** 状态再写回。

实现：`backend/app/gateway/routers/mcp.py`。

写入后仍建议 **重启 LangGraph**，保证工具列表与 MCP 缓存一致。

### 5.3 MCP 工具很多时

在 **`config.yaml`** 中启用：

```yaml
tool_search:
  enabled: true
```

使 MCP 工具可延迟发现，减轻单次上下文中的工具 schema 体积。逻辑见 `backend/packages/harness/deerflow/tools/tools.py`。

## 6. 自检清单（改完配置后）

- [ ] `.env` 中相关变量已设置，且 YAML/JSON 中 `$VAR` 无拼写错误。
- [ ] `extensions_config.json` 中对应 MCP **`enabled: true`**，`command`/`args`/`url` 在运行环境内可访问。
- [ ] 若使用 Guardrail / 权限策略，与 `docs/权限控制.md` 中的资源命名（如 `mcp:server:tool`）一致。
- [ ] 重启后在前端或日志中确认工具已出现；异常时查 Gateway 与 LangGraph 日志。
