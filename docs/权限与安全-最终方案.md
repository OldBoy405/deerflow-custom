# DeerFlow 权限与安全最终方案（整合版）

本文在 **`docs/权限控制.md`（RBAC + ABAC + Guardrail）** 与 **网关 / 数据层租户横切（单库多租户、thread 归属）** 之间做对齐，形成一套可分工实施、互不打架的企业级方案。

---

## 1. 两套方案各自解决什么

| 维度 | `权限控制.md` 侧重 | 先前「横切」方案侧重 |
|------|-------------------|----------------------|
| **主战场** | **工具执行前**：谁能调哪个 `tool` / 访问哪个 `kb` / 哪个 `mcp:*` | **请求与数据入口**：谁属于哪个租户、能否操作某个 `thread`、磁盘与记忆是否串租户 |
| **机制** | Postgres 存策略，`MyGuardrailProvider`，deny 优先、默认拒绝 | Gateway 解析 JWT → `tenant_id` + `subject`；Store/Paths/记忆等带租户键；可选 RLS |
| **资源模型** | 统一 `resource_key`（`tool:` / `kb:` / `mcp:`） | 资源是 **thread、上传路径、记忆行、checkpoint** 等「平台对象」 |
| **身份字段** | `sub`、`dept`、`roles`、`tenant`（JWT） | `tenant_id`（= 租户隔离键）、`subject`（= 通常等同 `sub`） |

**结论：二者互补，不是二选一。**  
- **没有数据层隔离**：仅有 Guardrail，仍可能出现「猜中 `thread_id` 读别人会话」类问题。  
- **没有工具层策略**：仅有租户与 thread 校验，仍可能出现「同租户内越权调 `bash` / 越权读知识库」。

---

## 2. 统一概念与命名

| 概念 | 建议约定 |
|------|-----------|
| **租户** | JWT `tenant`（如 `corp.cn`）→ 服务端统一为 **`tenant_id`**，贯穿 Gateway、Store、记忆 PG、（可选）策略里 `namespace` 前缀校验。 |
| **主体** | JWT `sub` → **`subject`**（与 `users.user_id` 对齐）。 |
| **组织与角色** | `dept`、`roles[]` 仅用于 **RBAC/ABAC 策略引擎**（`权限控制.md`），不替代 `tenant_id`。 |
| **会话** | `thread_id` 必须绑定 **`tenant_id` + `subject`（owner）**；列表/继续会话 API 先校验归属再进入 LangGraph。 |

---

## 3. 最终架构：三层防线

### 第一层：入口身份与租户（Gateway / LangGraph 前置）

1. **JWT 校验**（或企业网关已校验，后端只信 `X-Forwarded-*` 或签名 claims）。  
2. 注入 **`request.state` / `runtime.context`**：`tenant_id`、`subject`、`dept`、`roles`（claims 原样或规范化）。  
3. **Thread 类 API**：`POST/GET/DELETE /threads`、`runs` 等 — **强制** `tenant_id` + 校验 thread 元数据中的 owner（或与 Store 命名空间一致）。  
4. **路径与记忆**：`Paths`、记忆 PG 行、（可选）checkpoint 元数据 — 读写均带 **`tenant_id`**，**RLS** 或等价应用层 WHERE。

**与 `权限控制.md` 的关系**：同一套 JWT；第一层消费 `tenant` + `sub` 做**数据隔离**，第二层消费 `dept` + `roles` 做**策略判定**。

---

### 第二层：工具 / 知识库 / MCP 授权（Guardrail）

1. 启用 `config.yaml` **guardrails**，使用 **`MyGuardrailProvider`**（或等价实现）。  
2. **每次工具调用**前：根据 `tool_name`、`tool_input` 解析 **`resource_type` / `resource_key` / `action` / `namespace`**（见 `权限控制.md` §2、§8）。  
3. 查询 Postgres **`policies`**，执行 **`condition_json`**（ABAC），**DENY 优先**，默认拒绝。  
4. **知识库 / RAG**：当访问路径或 MCP 参数隐含 `namespace` + `kb_id` 时，映射为 `kb:<namespace>:<kb_id>` 参与策略。  
5. **审计**：写入 **`authz_audit_logs`**（可异步）。

**与第一层的关系**：同一请求已具备 `subject`/`dept`/`roles`/`tenant_id`；Guardrail 只读这些字段 + 工具上下文，**不**负责 thread 列表的 CRUD 授权（由第一层完成）。

---

### 第三层：数据与密钥（最小权限）

1. **数据库**：业务 PG（策略表）与记忆 PG（若分离）连接账号**最小权限**；记忆表 **RLS** 绑定 `tenant_id` / `subject`。  
2. **MCP / SQL**：连接串与账号按环境拆分；**低权限 DB 用户** + 行级/视图权限，避免「一个 MCP 账号拖库」。  
3. **可选**：策略查询结果 **短缓存**（`user + resource_key + action`），注意租户键纳入缓存键。

---

## 4. 判定顺序（单次用户消息 → 工具执行）

建议固定顺序，避免重复与歧义：

1. **认证**：JWT 有效、未过期。  
2. **租户与 thread**：若本请求绑定 `thread_id`，校验 **租户 + owner**（及管理员例外策略若需要）。  
3. **运行智能体**：消息进入图状态（checkpoint 已按 thread 分区）。  
4. **工具调用前**：**Guardrail**（`权限控制.md` 模型）→ ALLOW 才执行。  

若在第 2 步失败：返回 **403/404**（不泄露他租户资源是否存在）。  
若在第 4 步失败：返回工具层 **拒绝** + 审计记录。

## 5. JWT Claims 统一建议（合并两方案）

在 `权限控制.md` §7 基础上，强调与数据层一致：

```json
{
  "sub": "u_fin_001",
  "dept": "FIN",
  "roles": ["viewer", "finance_editor"],
  "tenant": "corp.cn",
  "exp": 1893456000
}
```

- **`tenant`**：必填（多租户场景）；映射 **`tenant_id`**。  
- **`sub`**：必填；映射 **`subject`** 与 `users.user_id`。  
- **`dept` / `roles`**：供策略引擎；可与 `users` / `user_roles` 表同步或仅信 JWT（企业自定，需防伪造则必须校验签名 + 可选服务端拉取用户信息）。

## 6. `resource_key` 与「平台资源」的并行

| 类型 | 命名示例 | 在哪一层处理 |
|------|-----------|----------------|
| 内置工具 | `tool:bash` | Guardrail（第二层） |
| MCP 工具 | `mcp:notion:query_database` | Guardrail |
| 知识库 | `kb:corp.cn.finance:kb_invoice_001` | Guardrail +（可选）namespace 与 `tenant` 一致性校验 |
| 会话 thread | 不强制用 `resource_key` | 第一层：元数据 + Store 命名空间 |
| 上传/产物路径 | 虚拟路径 + 宿主路径 | 第一层：tenant/thread 解析 |

若希望 **thread 也进统一策略表**，可扩展 `resource_type = 'THREAD'` 与 `resource_key = thread:<id>`，由 Guardrail 或专用中间件评估；**默认**仍以第一层 API 校验为主，成本低。

## 7. 实施路线（建议）

| 阶段 | 内容 |
|------|------|
| P0 | JWT → `tenant_id` + `subject` 注入；thread CRUD 归属校验；默认拒绝未知 thread |
| P1 | 执行 `docs/sql/authz_init.sql`；实现 `MyGuardrailProvider` + 审计 |
| P2 | 记忆 / Paths PG + RLS（见 `docs/记忆优化.md`）与 `tenant_id` 对齐 |
| P3 | 策略缓存、异步审计、策略版本化（见 `权限控制.md` §11） |

## 9. 一句话总结

**`权限控制.md` 管「能执行什么工具、能碰什么知识库」；横切方案管「是谁、属哪租户、能不能动这条会话与这份数据」。** 合并后的最终方案 = **入口租户 + thread 归属 + Guardrail RBAC/ABAC + 密钥与 RLS 最小化**。
